The words Fleet's pages and screens use: the planning words first, then the words of the running loop. Look a word up here when a page or a screen uses it without explaining it.
:::

## Planning words

| Word | What it means |
|---|---|
| **acceptance criterion** | One line of a PRD that states something the running product must do, written so it can be shown to pass or fail. |
| **API key** | A key you create in Settings that lets your own tools, such as a terminal agent, call Fleet as you. |
| **audit** | A check of a whole stretch of the product against one checklist, such as security or UI, that files what it finds as issues. |
| **box shell** | A terminal on a machine itself, outside any session, for looking at its disks, logs or processes. |
| **capability** | One concrete thing the product lets a person do, small enough to check at any time and still true tomorrow; it sits under one use of a feature, is shipped by a PRD, and never finishes. |
| **check result** | One small file under `knowledge/audits/results/` that records one run of a check: what it looked at, the verdict and the evidence. |
| **Cockpit** | The first page in the sidebar: one list of everything waiting on a person, one row per item, beside everything that was filed. |
| **command** | One step of Fleet's work, such as `bug:fix` or `slice:create`, written as a markdown file that a session runs. |
| **component** | A part of the product you can point at in the code, such as a directory, a service or a set of tables; it is built and never finishes. |
| **decision** | A fork someone took in the knowledge base, recorded with the option chosen, the option refused and the reason. |
| **dock** | The panel beside a large session in the Terminals page that shows the machine's figures and the session's tabs. |
| **feature** | A part of the product a customer would name, such as sign-in or parts management, described by a short brief and a few uses; it never finishes. |
| **feature area** | The planning name for a feature: every slice, PRD, task and bug is filed under one. |
| **feature brief** | The few lines at the top of a feature's page: one summary sentence, the problem it solves, an example of a real person using it, and what it is not. |
| **feature map** | The file under `knowledge/features/` for one feature, holding its brief, its uses and the capabilities under each use. |
| **feature request** | What you file from **Feature request** in the sidebar: something the product should let people do, which Fleet places in a feature before anything is planned. |
| **filing** | A feature request, bug or task a person filed, with its own key, which Fleet takes from there. |
| **Human WIP** | The position an issue moves to when a person takes it by hand, where the fleet starts no work on it until that person hands it back. |
| **intake interview** | The agent that reads a new feature request against what the product already promised, asks where it goes, and asks its filer what it cannot work out. |
| **journey** | How one kind of person gets a whole job done in the product, written from the real reason they open it. |
| **knowledge base** | The `knowledge/` folder a repository keeps beside its code, saying what the product does, what it promised and what is changing. |
| **ledger** | The verifier's list of what a fix has to make true, one line per claim, each proved or left open at the pull request's head. |
| **misfit** | A capability row that fits no use of its feature; it waits under a last `### Misfits (to move)` heading until a person decides where it goes. |
| **mockup** | Clickable pages an agent drew to show a design, attached to the question that asks you to approve it. |
| **outcome** | A lasting property that comes from several components working together and owns no code of its own, such as "an order page loads in under a second". |
| **Parked** | The tracker position that takes an issue away from the fleet, with no reason or date, until someone moves it back. |
| **planning hold** | A note your own session gives the fleet that it is doing a planning step itself, so the fleet does not start the same step. |
| **planning ladder** | The fixed list of tests, in order, that decides what kind of work a request is: bug, idea, component, capability, outcome, feature area, theme, task, PRD, slice or program. |
| **planning mode** | A repository's setting that says whether new work is grouped under programs or under feature areas. |
| **plugin** | A folder Claude Code can load to add commands to a session; Fleet writes its commands into `.fleet/` as one. |
| **PRD** | A piece of work one agent builds in one session, with acceptance criteria, and the only thing whose status anyone writes. |
| **program** | A larger result that two or more slices add up to and none delivers alone, used only by repositories that plan by programs. |
| **promise** | Anything the product committed to that a check can prove: a requirement, a shipped capability or a journey's acceptance criterion. |
| **proof** | The check, named on a program or slice, that shows it works end to end for a real person or on a real screen. |
| **register** | The file under `knowledge/requirements/` that holds one domain's requirements, each with a permanent id. |
| **reproduce stage** | The step after a bug is filed where an agent tries to make it happen and writes a test that fails because of it. |
| **requirement** | One sentence the system must always, or must never, do, kept with a permanent id in a register. |
| **responsible** | The people named on a program as the ones who answer for it. |
| **retro** | What an agent writes after it finishes a run: what went well, what got in the way and what it would change. |
| **route proposal** | The route step's answer to what kind of work a filing is and where it belongs, which a person accepts or sends back. |
| **scenario** | A check the QA agent writes that walks several parts of the product together, each expected result proving one promise. |
| **screening** | The step where a person reads a customer's exact words and approves them before any agent is given them. |
| **seat** | One place on a machine for a session; each seat holds one session at a time. |
| **secret** | A password, token or key Fleet stores for you and hands only to the sessions you attach it to. |
| **session** | An agent you talk to, or a terminal you type into, running on one of your team's machines in its own checkout of a repository. |
| **Shaping** | The planning step that turns a bare program, a name and a sentence, into its narrative, gaps, slices and proof. |
| **slice** | One deliverable with a one-sentence "Done when", which finishes by itself once its PRDs are done and its proof has shipped. |
| **slot** | One question a command asks about the repository it runs in, and the place where the repository answers it. |
| **Snooze** | Fleet's own hold on an item waiting on a person, which takes it out of everyone's Cockpit until the day you chose and then brings it back. |
| **task** | Small, scoped work that needs no design decision and gives nobody anything new to see or use. |
| **use** | One of the main things a person can do with a feature, such as "Sign in with SAML", with one plain sentence and a state read from the work under it. |
| **verifier** | A fresh session that never wrote the work and checks it from the evidence before it counts, such as a fix before it merges. |

## The running fleet

| Word | What it means | How to tell |
|---|---|---|
| **Machine (box)** | A machine that has told this API what it can do and keeps saying it is still there. Fleet never reaches out to a box: a box polls in, takes work it is capable of, and reports. So a box that stops reporting has not stopped — it is unaccounted for, which is a different and worse thing. | Did it say hello, and has it said anything since? |
| **Repository (lane)** | A repository, and the checkout of it a box works in. Every box can work every lane; which one an issue goes to is a property of that issue, not of the machine. A box offers a lane when it has the repository cloned, is not known to be unable to push there, and is not carrying a checkout whose commit gate is known to be off — unknown is offered, because refusing on an unknown would idle a fleet over a question nobody asked. | Is there a checkout of that repository on that box? |
| **Hooks state** | The commit gate's standing in one lane's checkout, as the box derived it from disk. The push credential says whether finished work can leave the box; this says whether the repo's own gates ran on the commits before they did. Two of thirteen boxes once took work with the gate quietly off and read as healthy on every field, which is why the state exists as five words and not as a boolean — and why only `failed`, the one answer reached by looking at a checkout that declares the gate and finding the hook gone, routes a box out of a lane. | Will commits made in this checkout run the repo's own gates? |
| **Stage (dispatch position)** | Where an issue is in its lifecycle — one field, always present, and the tracker's own workflow-state name rather than a shadow of it. The position IS the claim: four positions dispatch, two mean an agent already holds it, and the rest are parks, human holds or endings. | Would a box take this issue right now, and to do what? |
| **Assignment (claim)** | The right to be the box running one issue. Taking work is a transaction: two boxes cannot hold one issue because a unique constraint says so, not because a race usually resolves the way you hoped. A claim is never deleted — releasing one expires it — because the row is the only memory of how many epochs the issue has had. | Is there exactly one box entitled to report on this issue? |
| **Assignment's lease** | How long a claim lasts. It is renewed by reporting progress and by nothing else — there is no evidence-free ping, so a box cannot hold an issue for a session it has stopped watching. An expired lease is not renewable: the holder must take the claim again, which advances the epoch, which is what makes the retake safe. | Has the box holding this said anything about it recently enough? |
| **Take (epoch, fencing token)** | Which take of a claim you are in. It counts up by one every time the issue is claimed, and every write made on a claim's behalf presents it. A write under an older epoch is refused. This is what stops a box whose lease expired — but which is very much alive and still running a session — from reporting over the top of its successor. | Does this write name the epoch the claim is actually in? |
| **Run** | One attempt at one issue on one box. It ends in exactly one outcome, and the outcomes are never summed: reading "3 failures" when two of them were an engine refusing to start is being misled. Only some outcomes charge an attempt against the retry budget, because a crash carries no verdict and a refutation is a verifier working correctly. **Every** outcome counts against the separate run ceiling, which is what bounds an ending nobody is charged for. | Did a box start a session for this issue, and how did that session end? |
| **Token floor** | What a run's stored token counts actually are, which is **less than a total and never a zero**. The figure is the HIGHEST cumulative count a box ever reported, so a session that stopped reporting before it ended is short by whatever came after it, and one whose daemon restarted mid-run is short by whatever the restarted session had not yet overtaken. A counter nobody read is `null`, which is an absence rather than a measurement of nothing — and rows written before that distinction existed spell both as `0`, which no column can now tell apart. | Is this number a measurement, a measurement of zero, or nobody having looked? |
| **End cause** | **Why** a run ended, which is a different question from what it concluded. A run that reported `failed` and SAID so is a session that did its work and judged it; one that reported `failed` because nobody could read the word it wrote is a missing row in a table here, and nothing about the box, the engine or the work is wrong. The two were the same word until this existed, and telling them apart took an ssh session and a file on the machine. | What ended this run — and is the thing to fix the work, the box, or us? |
| **Cost state** | How well a run's spend is actually known. Never rendered as money and never served as money (Fleet never shows money) — this is about the RECORD's own provenance, kept for the same reason a nullable-with-provenance type is kept even where its value is never displayed; the state is what travels to a page, as `measurement` on a run, and the figure stays in the record. The figure only lands when the engine emits a final result, so a session stopped mid-turn recorded a bare zero after real spend — and that zero cannot be told from a run that was free. Three of the five values carry no number at all, which is the point: nobody looked, there is nothing to look at, and the call failed are three different answers and none of them is a zero. | Was that run's spend measured, measured in part, or not at all? |
| **Decision** | What the API chose to dispatch, for which issue, and on what inputs — recorded so the choice can be re-argued later without re-deriving the world it was made in. A decision is either executed or shadowed. Shadowed means decided for real and executed nothing, which is how a cutover is de-risked, and the two counts are never added: a total merging them destroys the only measurement the exercise produces. | Can you say why the fleet is doing this rather than that? |
| **Candidate set** | One read of the tracker, projected into this database, that the dispatcher orders over. It exists so that claiming is a transaction with no network call inside it. Its failure is invisible everywhere else: a projection that stopped refreshing leaves a perfectly coherent set installed, so the boxes stay busy, the leases stay renewed, and the fleet works yesterday's board with nothing red. | Was this decided against the tracker as it is now, or as it was? |
| **Outbox** | An intended write to the tracker, committed in the same transaction as the decision that produced it and drained by a separate worker. Without it a decision can be durable here while the tracker never hears it, and the two diverge in silence. So an undrained outbox is an incident rather than a queue length: every row in it is something this database decided that the tracker does not yet say. | Does the tracker say what this database decided? |
| **Engine and slot** | Which coding-agent CLI drives a session, and how many at once a box will host. The engine is chosen per agent rather than per machine. A box that has not published what it can run is treated as having no slot — the safe direction, because handing work to a machine that never said it could do it is how work disappears. | Did the box say it can run this, and does it have room? |
| **Workstation session** | A session on a box that a person asked for: one command, in one checkout, still running whether or not anyone is watching. Two kinds ride the same lifecycle — a `terminal` (tmux pane, opaque launch string) or an `agent` (ACP child, engine and model recorded instead). It is not a run — nothing was dispatched and nothing is being attempted on an issue — and it is not raced for, because a session somebody is sitting in cannot be re-run somewhere else if the machine dies. | Is there a real session on a real machine behind this row, and of which kind? |
| **Session host (in boxes / on the host)** | Where a machine runs its Fleet sessions, chosen per machine by `FLEET_SESSION_HOST` rather than per session. **In boxes** means each session runs inside a Sysbox box of its own — its own filesystem and process tree — so the machine's credentials, its disk and every other session on it are out of that session's reach. **On the host** means sessions run as ordinary processes of the machine itself, sharing its disk, its credentials and its process table with every other session on it. Two internal nouns: a **box** is the isolated container one session is given, and the **host** is the machine that ultimately runs every box and every session on it. | Would this session's mistake land in its own box, or on the machine? |
| **Probe** | Whether anybody has actually looked at a workstation session, and what the look returned. It is four values rather than a yes/no because "the box could not ask" and "the box asked and it is not there" are opposite claims. Collapsing them would close every terminal on the screen during one hiccup, and closing is not recoverable: the person's session is still running and Fleet now says it is gone. | Did somebody look, and did they get an answer? |
| **Attempt and retry budget** | Two different numbers that a single word used to cover. The **reported attempt** is the box's own stamp — the try it believed it was on — and is useful for lining a run up against that box's logs. The **retry budget** is derived: the runs since the newest reset whose outcome charges. They genuinely disagree, because a run whose box died still counts toward the derivation while a box that never reported never stamped anything. A human clears the budget by drawing a line, never by deleting history. | Is this the number the box wrote down, or the number the runs add up to? |
| **Rank** | Why the fleet is working this rather than that. Exactly one list is authored — programs and slices, in the order somebody wrote them — and everything else inherits, so there is never a second order to disagree with the first. A claim keeps the rank it was taken at, because a sync that reshuffles the board must not retroactively change why something was picked up. | Can you name the row this urgency came from? |
| **Draining** | A box that is still reporting, still finishing what it holds, and taking nothing new. It is reported beside a box's liveness rather than folded into it, and that is deliberate: draining is not a fifth thing a box can be, it is a thing a working or idle box is also doing. A page that made it a state would have to choose between saying a machine is busy and saying it is going away, and both are true. | Is it still reporting, and will it take the next piece of work? |
| **Never opened** | A seat that was provisioned, registered, published what it can do — and has never taken a single run, with nothing that will ever be offered to it. It is not the drain flag above under another name: a box being retired is draining WITH runs behind it and is doing exactly what it was told, while this one has a bring-up that stopped half-way. Provisioning arms two independent stops on a fresh box, **FLEET_DRAINING=true** in the EnvironmentFile and an absent **/etc/fleet-daemon/in-service** marker, and a human who lifts one of the two gets a box that is registered, heartbeating, fully probed and idle forever. Four seats sat like that on 2026-09-05 with every check green. Reported beside the liveness state and never folded into it, for the same reason draining is: it is a thing that is true OF an idle or ineligible box, not a sixth thing a box can be. | Has this box ever taken work — and can it still be given any? |
| **Cannot take work (ineligible), and why** | Every structural reason a box can never be given work, whatever the board holds — answerable from what the box published, with no lease and no candidate involved. A box can carry more than one at once, and the API names all of them rather than the first, because a box with no lane AND no engine needs both fixed before one dispatch reaches it. System → Machines says each reason in a person's words on every box that carries it — the words each row below leads with, beside the code — and the sentence below is repeated on the row only when nothing else on this page already carries it and no other box's row says the identical thing. | Would this box be offered work out of any queue that will ever exist? |
| **Pane** | Whether the terminal in a workstation session was changing when the owning box last looked at it. Three answers rather than two: not read is not the same as not busy. A box that could not look has learned nothing, and rendering that as idle would be the page inventing an observation nobody made. | Did the box look at the screen, and was anything moving on it? |
| **Sync** | The reading of the corpus this board is drawn from: one commit, fetched, parsed whole, and stored as a generation. A board is always a reading of one commit rather than of "the repository", so the question a reader has is not whether the service is up but whether what is on the screen is the corpus as it is now. Four different silences look identical on a page that does not name them, and an empty board is not the same as one nothing has ever synced. | Which commit is this, and is it the one being served? |
