# Fleet, for agents

This is the first file to read in a repository that uses Fleet. It says what Fleet is, how its
work is organised and which rules bind you. It is generated by `fleet commands sync` and is the
same in every repository that has the tier; this repository's own rules live in its own rules
file, and where the two differ the repository's own rule wins. Do not edit anything under
`.fleet/` by hand: the next sync overwrites it. A change to a command or to this file is made in
Fleet's own source and arrives here as a new release of the tier.

# What Fleet is

Fleet plans, builds and checks the work in this repository against its **knowledge base**: the
plain files under `knowledge/` that say what the product is made of (components), what people can
do with it (capabilities), how they get a whole job done (journeys), what it has promised
(requirements), what was decided, and what is being changed (slices and PRDs). Read it before
you build, and keep it true when you change the product.

Fleet's work is done by **commands**, each a whole procedure run the same way every time, and by
**gates** that keep the party that wrote a change from certifying it. Work is tracked as issues
that move through **positions**; Fleet's tools, not the tracker's own API, are how you read and
move them.

# The knowledge base

Each kind of file has a place on one ladder. Know which rung you are on before you create
something; `.fleet/docs/knowledge-base/what-is-it.md` walks it.

| Rung | What it is | Kept as |
|---|---|---|
| **Component** | a part of the system someone builds; durable, never "finished" | a row in the component registry |
| **Capability** | something a person can do with the product | a row in a feature map |
| **Feature area** | a bucket of capabilities a customer would name | a feature map under `features/` |
| **Journey** | how one kind of person gets a whole job done | a file under `journeys/` |
| **Program** | a larger result that two or more slices add up to (only where the repository plans by programs) | a register row |
| **Slice** | one deliverable with one sentence that says when it is done | a register row and optional detail file |
| **PRD** | one piece of work one agent can build in one session, with checkable acceptance criteria | a folder under `prds/` |
| **Requirement** | a commitment: a rule, a ceiling, a refusal | one numbered row in a register, cited by id |
| **Decision** | a choice, the option turned down and why | a dated file under `decisions/` |

- **Durable versus versioned.** Components, journeys and feature maps are durable: they are never
  "shipped". Programs, slices and PRDs are versioned: they finish.
- **Ship-state is derived, never written.** Only a PRD carries an authored `status:`. A slice or
  program is complete when the PRDs and proof under it say so; never write a status on either, and
  never restate a capability's shipped or planned state in a map. Read it from the PRD.
- **Prose cites a commitment, it does not restate one.** A "shall" or "never" is one numbered
  requirement row with a permanent id that is never reused or deleted. Write the id; do not copy
  the sentence.
- **Generated files are never hand-edited.** Some tables are rendered from one file per row; see
  `.fleet/docs/knowledge-base/generated-tables.md`. Edit the source row and regenerate.
- **Maps keep structure, not intent drift.** When you change code a feature map claims, update the
  map's ledger (rows, surfaces, source paths) and leave its stated intent alone.
- **Read a PRD's `status:` first.** A stub is not ready to plan or build; the next move for a stub
  is to author it, not to implement it.

The next section, at the end of this file, is the table of file types: which docs page to read
before you create or change a file of each kind.

# Commands

Commands are named `noun:verb`: the artifact is the namespace and the lifecycle stage is the verb.
Start a session with one; type `/` to list them, or open the file under `.fleet/commands/`.

- **Create** commands file well-formed work or author an artifact: `idea:create`, `bug:create`,
  `task:create`, `prd:create`, `component:create`, `slice:create`, `program:create`.
- **Execute** commands drive work to a pull request: `bug:fix`, `task:implement`, `prd:implement`.
  They open a green PR and hand it off. They do not merge their own work.
- **Gates** sit between them. `/fleet:check` triages every newly filed issue in a session the
  filer never touched. `/fleet:verify` and `/fleet:prd:verify` certify a change in a session
  the author never touched, then merge it or send it back.
- **Cross-cutting**: `ask` (a question, no building), `intake` (a short interview that turns an
  idea into a clear request), `route`, `push` (commit and open a PR), `unblock` (drain the queues
  that wait on a person).

# How work moves

An issue sits in one **position**, and the position says what runs next. The full list is
`.fleet/docs/reference/issue-positions.md`; the ones you will meet:

- **Intake Queue** and **Triage Queue**: filed, not yet checked. The check releases an issue to
  the Implement Queue, escalates it to a person, or closes it.
- **Implement Queue** and **Rework Queue**: ready to build. Rework carries the verifier's open
  points back to the implementer.
- **Verify Queue**: a green PR waiting for an independent verifier.
- **Triaging**, **Implementing**, **Verifying**: the claimed positions. The position is the
  claim; two sessions never drive one issue.
- **Blocked · decision**: a person must answer. **Blocked · action**: a person must do something
  no agent can. Neither is a place to leave work you could finish.

Fleet moves an issue between positions; do not move it by hand unless a command tells you to.

# Rules that bind every session

- **The author never certifies its own work.** Whoever wrote a change does not approve or merge
  it. Open a green pull request and hand it to the verify gate. Never merge past that gate, and
  never use an admin override to do so.
- **Build what was promised; never promise something new.** Adding customer-facing functionality
  is a person's decision. If you find work the product has not committed to, file it for triage
  and stop; do not build it, and do not add features, settings or abstractions the task did not
  need. Craft is yours; scope is the person's.
- **Reproduce before you fix.** A bug fix starts from a failing test that shows the defect, then
  the root cause, then green. Never patch a symptom.
- **A flaky test is a bug.** Fix the cause, key the wait off the real event, and never answer it
  with a longer timeout, a retry or skipping the hook.
- **Credentials never go on a command line.** Arguments are visible to every user of the machine
  and end up in logs. Pass a secret through the process environment or standard input.
- **Never commit a secret**, in the tree, a comment or a fixture.
- **Generated files stay generated.** Anything produced by a generator is changed at its source
  and regenerated. That includes everything under `.fleet/`.
- **Stay in scope.** A separate defect you find is filed as its own issue, not fixed inside an
  unrelated change.
- **Say why.** A commit message and a PR description give the reason and name the work item.

# Asking a person

When a decision belongs to a person, ask with the `ask` tool; do not guess and do not print the
question and carry on. The person has not read the issue, the PRD or the code, so a question must
stand alone: say what the work is, give one concrete example, explain each internal term the first
time it appears, and offer two to four options with the recommendation first and a reason on every
option. Never put a bare id in an option. When the answer arrives, act on it in the same run and
write it into the issue description, not only a comment. On a headless fleet run `ask` returns
`parked`: end your turn.

# Issues and tools

Read and change issues through Fleet's tools (`get_issue`, `search_issues`, `file_issue`,
`move_issue`, `triage`, `comment`, `ask`, `decide`). A session holds no tracker credential and
calls no tracker API or tracker MCP server directly. Use only label and state names the tools
return; a typo creates a real label or silently fails to move the issue. The tools are listed in
`.fleet/docs/reference/mcp-tools.md`.

# Pull requests

Every change reaches the main branch through a branch and a pull request, never a direct push.
Arm auto-merge when you open the PR, and then **own it until it is merged**, not until it is
green. Watch for the ways a green PR still does not merge:

- a failed check;
- a merge conflict (a conflicted PR runs no checks at all, so "no checks" means conflict until
  proven otherwise);
- the PR head differing from the branch you pushed (confirm they match after every push);
- removal from the merge queue (read the failing queue run, fix, re-enqueue);
- a token missing the scope a workflow-file change needs.

Resolve a conflict by rebasing onto the main branch; never hand-merge a generated file, regenerate
it. Never skip a hook or force past a failing check.

# The tier

`.fleet/` is a Claude Code plugin holding Fleet's commands (`commands/`), the process documents,
registers and rubrics they cite, Fleet's docs (`docs/`) and this file. Nothing in it is loaded by
an engine that was not told to: a Fleet session loads it, and so does anyone who opted in. A
repository's own additions go under `.fleet/local/`, which the sync never touches.

# Before you create or change a file under `knowledge/`

Read the docs page for that file's type first. It says what the file is, what it must carry and
what not to put in it, and the `knowledge-types` check refuses a file that does not match.

| File | Lives under `knowledge/` | Read |
|---|---|---|
| Journey | `journeys/flows/*.md`, `journeys/maps/*.md` | `.fleet/docs/knowledge-base/journeys.md` |
| PRD and its design, plans and mockups | `prds/<NNNN-slug>/` | `.fleet/docs/knowledge-base/prds.md` |
| Feature map (a feature area, its uses and capabilities) | `features/*.md` | `.fleet/docs/knowledge-base/feature-areas.md` |
| Requirement (a numbered promise) | `requirements/*.md`, `requirements/rows/*.json` | `.fleet/docs/knowledge-base/promises.md` |
| Decision record | `decisions/*.md` | `.fleet/docs/knowledge-base/decisions.md` |
| Slice | `slices.md`, `slices/rows/*.json`, `slices/*.md` | `.fleet/docs/knowledge-base/slices.md` |
| Program | `programs.md`, `programs/rows/*.json`, `programs/*.md` | `.fleet/docs/knowledge-base/programs.md` |
| Component | `specs/architecture/components.md` | `.fleet/docs/knowledge-base/capabilities-and-components.md` |
| Slot (this repository's answer to a command) | `slots/*.md` | `.fleet/docs/knowledge-base/slots.md` |
| Record (audit, retro, check result) | `audits/`, `retros/` | `.fleet/docs/knowledge-base/records.md` |
| Generated table or fragment (never hand-edited) | `**/*.md.tmpl`, `**/rows/`, `scripts/*.py` | `.fleet/docs/knowledge-base/generated-tables.md` |
| Anything else (spec, SOP, product vision, README, environment) | `specs/`, `sops/`, `strategy/`, `environments/` | `.fleet/docs/knowledge-base/the-folder.md` |

A type not listed here is on `.fleet/docs/reference/knowledge-file-types.md`, which names every type, where it lives
and the front matter it needs. Before you add a new journey, slice, program or PRD, sort out what
kind of thing it is with `.fleet/docs/knowledge-base/what-is-it.md`.
