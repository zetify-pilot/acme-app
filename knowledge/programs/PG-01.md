# Customers can export their tasks as CSV.

A customer can take their whole task list out of the app as a CSV file and open it in their own spreadsheet. Priya, who runs the Tuesday delivery meeting, presses export and gets one row per task — its title, and whether it is done.

**For example.** Priya runs the Tuesday delivery meeting. Today she reads her task list on screen and types the still-open ones into her own spreadsheet — about twenty minutes of work that is out of date the moment somebody ticks a task off. After this, she presses one button and gets a file with one row per task: the task's title, and whether it is done. She opens it straight in Excel, sorts it, and pastes it into her report. If her list is empty she gets a file with the column names and no rows, rather than an error, and if her list is ever too long to come out in one piece she is told so in words instead of being handed a broken file.

**Who it's for, and when.** For whoever runs the weekly planning or delivery meeting. *When I have to report on what is open and what is done, I want to take my task list away as a spreadsheet, so I can build the report from the real list instead of retyping it.*

**Today.** The app shows the tasks and does nothing else with them. To report on them, Priya reads them off the screen and types the open ones into her own spreadsheet by hand — and because the meeting is weekly while the tasks move all week, what she typed is already wrong by the time anyone reads it. There is no way to take the list away in any shape at all.

**Why now.** A copy in a spreadsheet is the first thing people reach for once their tasks matter to them, and it is the smallest honest test of a larger promise: that a customer can get their own data out without an engineer doing it for them. The earlier a real list comes out, the sooner we learn whether the file is shaped the way people actually want it.

**What changes for them.** One action, one file. A customer presses export and gets their tasks as a spreadsheet they can sort, total and paste into a report — one row per task, with its title and whether it is done. The file is theirs to keep and to use anywhere. An empty list still produces a file, with the column names and no rows. A list too long to come out in one piece produces a sentence a person can read, not a broken file. And the file holds their tasks, not everybody's.

**How we'll know.** The person who runs the weekly meeting stops retyping tasks into their own spreadsheet and opens the export instead. The file is used away from the app — opened in a spreadsheet tool, pasted into a report — rather than only looked at. And nobody writes in to ask us to send them their tasks.

**Not doing.** No bringing tasks back in from a spreadsheet; no format other than CSV; no scheduled or emailed exports; no spreadsheet-style view inside the app; and no choosing columns or a subset of tasks — the whole list goes out as it is. Deliberately not carried either, because the source was chosen as the app holds it today: tasks surviving a restart of the app, and many people exporting at the same moment.

## Program-specific work

None. Every requirement this decomposition found is durable product work — a second customer would benefit from each of the seven — so all of them sit in the tasks feature map's ledger rather than here. Nothing in this program is true only while the pilot lasts.

**Class sweep** (Phase 2's universal classes, plus the ones this product needs):

- **Surface** — where the customer drives it. Today: three JSON routes and no screen. The
  chosen day puts a person in front of a browser opening the export address, which the HTTP
  API satisfies without a UI being built. Carried as CAP-0001 and CAP-0002.
- **Verification** — how it is proven end to end: the composed proof, PRD 0001, driving the
  same address a customer uses. Not a component test asserting the file in isolation.
- **Hardening** — what the pilot depth bar presumes: text integrity (CAP-0004), the empty
  case (CAP-0005), the too-long case (CAP-0006). Deliberately *not* carried, per the accepted
  depth bar: concurrency, abuse resistance, and a record of who exported what.
- **Ownership** — whose tasks these are. Carried as CAP-0007, sorted to the product ledger by
  the requester, so it is work this program does rather than an arrangement the pilot makes.
- **Persistence** — deliberately out. The source was accepted as the app holds it today
  (in memory), so surviving a restart is not a requirement of this program.

**Unsatisfiable requirements: none.** Nothing this program needs is a state the product
forbids. Every gap is a matter of work not yet done, and each is reachable through a
sanctioned path — including CAP-0007, which needs an identity the app does not have yet but
does not need a state the app refuses to enter.

**The sort (Phase 4).** All seven requirements are durable, noun-phrased, and worth having for
a second customer, so all seven are product capabilities. The two genuinely borderline items
were put to the requester and both came back *product*: per-customer separation (CAP-0007),
and the answer for a list too long (CAP-0006). Program-specific work: none.

**Component finding — reported, not written.** This corpus has no component registry
(`knowledge/specs/architecture/components.md` is absent), so no component owns any of this and
`python3 knowledge/scripts/component_of.py app/main.py` answers `-` (unclaimed). Proposing a
component — one layer for the tasks service covering `app/`, owning the task list and its
export — is a person's act, so nothing was registered. Until it exists, the seven capability
rows carry no component home and the two cuts carry no `Components` cell.

**The cuts, and what each holds.** Cut by what ships together, not by component:

**The proof.** PRD 0001 — *A customer exports their own task list and opens it in a
spreadsheet* — is the composed demonstration: two people each open the export from the running
product and save their file, each opens it in a spreadsheet and sees exactly the tasks they put
in (including a title with a comma and a quote), and a person with an empty list gets a file
with only a header. It is **not** either cut's own proof, and neither slice's `Verified by`
names it. It lands in SL-002 and exercises SL-003's cut as well, so it can only run once
SL-003 has shipped.
