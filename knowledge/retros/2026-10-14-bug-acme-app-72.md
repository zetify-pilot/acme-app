## Root-cause synthesis (what was *actually* the problem)
- `TaskIn.title` had a `field_validator` that computed `value.strip()` **only to decide
  whether the title was blank** and then returned `value` unchanged. The model therefore
  normalised for the check but not for the value, so the untrimmed string was what got
  stored and what both `POST /tasks` and `GET /tasks` echoed.
- The fix belongs at the same boundary the two previous title fixes (`#2` blank, `#9`
  over-long) used: the input model. It is expressed **declaratively**
  (`model_config = ConfigDict(str_strip_whitespace=True)`) rather than by returning
  `value.strip()` from the validator, because the config strips **before every constraint
  runs** — the blank check, the `max_length=200` rule, storage and the response all see the
  same string. Returning `value.strip()` from the validator (the issue's first suggestion)
  also fixes the reported symptom, but leaves the model inconsistent: `max_length` would
  then judge the *raw* string while the *trimmed* one is stored, so `" " + "x"*200 + " "`
  would be refused as too long even though the title actually stored is 200 characters.
  Confirmed by probing pydantic 2.14: the config strips first, the validator does not.
- Nothing downstream needed changing: `create_task` storing `task.title` verbatim is correct
  once the input model produces the trimmed title. Stripping inside `create_task` would have
  been the symptom patch the issue's own ledger names as the second site.
