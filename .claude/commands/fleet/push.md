#  Push

Default: commit any pending changes, push the current branch, open a PR, and **arm auto-merge** (skip a third-party draft). With a mode argument, finish the branch differently (auto-merge on green CI / merge locally / keep / discard).

> **SOP:** the automated subset of this repo's SOP for the same job, where it has one.

This command **absorbs the former ``** — its **Commit contract** (near the bottom of this file) is the canonical commit discipline: stage everything, run pre-commit, fix every failing hook, never loosen a gate, and verify the SHA actually moved. `/fleet:prd:implement` sub-agents follow that same contract when they commit. <!-- -refs:skip -->

PRD lifecycle is repo-local; the branch name (per `slot:git-workflow`) is what links the PR to its PRD. **`<key>` is always the issue's own key — its team prefix plus its number** (the **`tracker-identity`** slot names the prefix). Resolve it from the issue itself, never hardcode a team code: a workspace or team move silently breaks auto-linking for any PR still carrying the old prefix, with no error surfaced anywhere. **A bare `<key>` mention anywhere in the branch/title/body only auto-*links* the PR to the issue — it does NOT complete it.** The de-facto closer for bug/task/cleanup issues is the **fleet daemon** (`_pr_completes_issue` title-shape + closing-keyword attribution → `_drive_to_done`) — the tracker's keyword auto-close is **dead** for this workspace ( disabled it;  confirmed `autoClosedAt` null on completing merges). A GitHub closing keyword (`Closes`/`Fixes`/`Resolves <key>`) remains the daemon's **strongest attribution signal** (and the completing-title forms `fix(<key>): …` / `[<key>] …` are the other arm). **Only `ship` mode composes a closing keyword** (it is the *completing* merge the verifying session performs); **`push` mode composes a bare `Refs <key>` link and never a closing keyword** (see the convention directly below). Every autonomous ship path verifies the closing keyword landed ( / ).

> **🛑 A PR that only *prepares* the work must not carry a closing keyword ().** The fleet daemon's `_pr_completes_issue` treats a closing keyword as a completing claim — and historically (before  disabled keyword auto-close;  confirmed it no longer fires) GitHub's tracker integration closed the issue the instant *any* merged PR body carried `Closes`/`Fixes`/`Resolves <key>`, reacting to the literal text, never to whether the PR did the work.  was the recorded case: its prep PR (`/-infra#98`) merged `2026-08-15T09:11:58Z` and  `completedAt` two seconds later with none of the work done. The rule still holds under the daemon closer: **a prep/partial PR references its issue with `Refs <key>` (a bare link — `Refs` is NOT a completing form) and never composes `Closes`/`Fixes`/`Resolves`. Only the PR that satisfies the issue's acceptance criteria carries a closing keyword — in this command that is the `ship` merge, the completing merge the verifying session performs.** `push` mode composes `Refs` and never a closing keyword; `ship` mode — the only closing author — composes and verifies `Closes <key>`.

> **🛑 ATOMIC SHIP (non-negotiable — [`autonomous-drive.md`](../../process/autonomous-drive.md) Rule F).** A PRD's `status: shipped` transition and its PR merge are **ONE atomic event**. The `status: shipped` change is committed as the **final commit on the work branch** — it rides the PR — so the squash-merge lands it on `main` *in the same merge commit*. **There is NO "merge, then write status" step.** A post-merge `chore: status: shipped` commit on `main` is **BANNED**: it opens a window where a merged PR has a non-`shipped` PRD (or vice-versa), which the frontmatter-as-truth model cannot self-heal. Both `ship` and `merge` below stamp the status *before* the merge so the merge carries it.

## Step 0: Determine mode

Inspect `$ARGUMENTS`. The default mode is `push`. If the first token matches one of these (case-insensitive, with or without leading `--` or `/`), use that mode:

| Mode | When to use |
|------|-------------|
| `push` (default) | Ready for review — push to origin, open a PR, **arm auto-merge** (), and stop. GitHub merges the moment the required checks pass — for a `Type:bug`/`task`/`cleanup` PR that includes the required the fix gate (red until `/fleet:verify` passes), for a PRD the plan gate (red until the verify stamp); non-lane work merges on green CI, which is that lane's whole gate. A third-party draft is never armed (a human pause is not ours to lift — and the fleet never drafts its own PRs: the  implementer draft hold is retired, ). The verifying session's `/fleet:push ship` still owns the confirming merge for gated work. |
| `ship` | **Open a PR and auto-merge on green CI** — the path autonomous flows delegate to. **No execute command calls it any more; it belongs to the VERIFYING session.** For a PRD that is **`/fleet:prd:verify`** (it certifies a green implement PR, then ships); for a bug/task/cleanup it is **[`/fleet:verify`](verify.md)** (it certifies the issue's cause ledger, then ships). `/fleet:prd:implement`, `/fleet:bug:fix` and `/fleet:task:implement` all open a PR, drive CI green, move the issue to the **`Verify Queue`** workflow state, and stop — the party that wrote the code does not merge on the strength of its own certification. Stamps PRD `status: shipped` as the final branch commit, pushes, opens a PR carrying the tracker issue key, waits for CI, then squash-merges — so the merge **atomically** ships the status (Rule F). Confirms it landed. Returns the confirmed merge SHA or `NOT MERGED — <reason>`. (Replaces the former direct-to-`main` mode.) |
| `merge` | Merge locally to the base branch and delete the branch, **bypassing the PR/CI gate**. Reserve for tiny self-approved chore branches; prefer `ship` now that CI is active. |
| `keep` | Stop here — don't push, don't merge, don't delete. The branch stays as-is for later iteration. |
| `discard` | Throw the branch away. Requires a typed confirmation token (see Step 3). |

Unknown tokens (or `$ARGUMENTS` empty) → default to `push`.

## Step 1: Pre-flight checks (all modes)

1. Identify the current branch via `git branch --show-current`. Capture as `<branch>`.
2. Verify the working tree is clean for `merge` and `discard` modes — if there are uncommitted changes, stop and tell the user to commit or stash (do **not** auto-stash; that's an explicit feedback rule). For `push`, **uncommitted changes are committed first via the Commit contract** (below) before pushing. For `keep`, uncommitted changes are fine. (`ship` is handed an already-committed verified SHA and asserts a clean tree — it does not auto-commit.)
3. Run `git log @{upstream}..HEAD 2>/dev/null || git log origin/main..HEAD 2>/dev/null` to see commits ahead. If empty *and* mode is `push` or `merge`, inform the user nothing is ahead and stop.
4. **If on `main` and mode is `push`:** first, when the work item's tracker issue key (`<key>`) is known, check for an already-open PR for it (`gh pr list --search "<KEY>" --state open --json headRefName`) and **reuse its branch** (`git fetch origin && git checkout <headRefName>` — fetch first, or you check out a stale local ref, or none at all; then move your commits onto it) rather than opening a second PR. Otherwise create a **deterministic** feature branch `agent/<type>-<key>` (e.g. `agent/fix-eng-160`, `agent/prd-0015-eng-152`) per the conventions in `tracking-and-execution.md` — no per-user prefix, no slug, so a retry on any box resolves the same name. **Include the tracker issue key** (`<key>`); for a PRD, look up its tracker issue (titled `[NNNN] …`) → its identifier. Fall back to `agent/<type>-<slug>` only if no key resolves. Use `git checkout -b <branch-name>` to move the commits and working tree — **the documented exception to "cut from a freshly fetched `origin/main`"** (`tracking-and-execution.md` → "Branch-naming convention"): the commits already exist on `HEAD`, so a fresh base point would orphan them, and step 2's unconditional `git fetch origin` + `git rebase origin/main` is what puts the branch back on a current base. Never stop and ask for the branch name.
5. **If on `main` and mode is `merge`/`keep`/`discard`:** stop and tell the user — these modes only make sense on a feature branch.
6. Run the lane's fast mechanical guards (`make preflight`). `preflight` is the conventional aggregate of the repository's fast, deterministic mechanical checks — the classes CI reds on without a single failing test — so the pre-flight and CI run the *same* checks rather than two copies that drift; on the  lane it is the size-guard baseline, policylint, harness negative-control, submodule-pointer and scope-manifest guards. **Keep this local pre-push check deliberately small — compile the changed packages at most; do not re-run the full unit/DB/e2e suites here.** Those heavy lanes belong to CI, and the whole point of a small pre-push gate is that it stays cheap enough to always run rather than growing into the heavy gate the fleet deliberately does not have. For `merge` and `discard`, **do not proceed if it fails** — for `push`, surface the failures but continue (the user may want to push WIP for collaboration).

## Step 2: Detect the work item from the branch name (push, ship, and merge modes)

Branch convention — `slot:git-workflow` is the authority; the four kinds of work
item it distinguishes, and what each carries:

| Kind | Work item |
|---|---|
| a PRD branch | PRD pipeline work — the plan's own file carries its `status:` |
| a fix branch | Bug fix — tracked in the tracker, no repo file to update |
| a task branch | Engineering task — no markdown footprint |
| a chore branch | Repo-meta / chore — no work item |

Capture `<NNNN>` (PRD number) when the pattern matches, and the **`<key>` tracker issue key** wherever the branch carries one. The key is what auto-links/closes the issue — make sure it ends up in the **PR title and body** even if it isn't in the branch (resolve it from the PRD's tracker issue titled `[NNNN] …` if needed). If the branch has no `<key>` segment and no key resolves, proceed without the link.

**A docs PR is classified from `slot:docs` — never from its title.** The slot says how the
docs are built and published, and that decides which lane the PR takes:

- **Plain markdown, no build step** → **doc-only**: it touches no compiled surface, so it
  merges on the required green checks, and the doc-only lane is its whole gate.
- **A built site** (the slot names a build/publish step) → **code-bearing**: it has a build
  surface, so it takes the code lane and the same required checks the code it builds carries.
  Its built output is **generated** — run the slot's build target, never hand-edit the
  generated artifact.
- **Degrade.** When the repository leaves `slot:docs` unfilled there is no build contract to
  read: fall back to the diff — a PR that changes only markdown is doc-only; one that changes
  a site's sources or build config is code-bearing. Never assume doc-only to skip a check.

## Step 3: Execute the mode

### Mode: `push` (default)

0. **Commit pending work (if any).** If `git status --porcelain` shows uncommitted changes, run the **Commit contract** (below) to stage + commit them before pushing — inferring a concise commit subject from the diff (and the branch's `<KEY>` key when present). If the tree is already clean, skip to step 1.
1. `git fetch origin`
2. **🛑 Rebase onto `origin/main` exactly once, immediately before a push — and only when the PR shows `CONFLICTING`.** `main` carries required-status-checks branch protection, **not** required-up-to-date protection, so a branch that is merely *behind* `main` is not a problem: GitHub still computes a merge ref and `pull_request` CI still runs on the head. The rebase is therefore **not unconditional** — run `git rebase origin/main` only when `gh pr view <pr> --json mergeable,mergeStateStatus` reports `CONFLICTING` / `DIRTY`. Step 5.7 is where that check lives once the PR exists; it is the **one** rebase of the push, done immediately before the push, never earlier and never merely to be current. **Never rebase just to be current:** each rebase rewrites every commit SHA and cancels the PR's in-flight CI — 129 runs were cancelled over 1.46 days, ~16% of all PR runner time, and 46% of the superseding pushes were base-sync rebases. A fresh branch cut from a freshly fetched `origin/main` (step 1.4) needs no rebase at hand-off at all. The one rebase a push **does** owe is the stale-base one: a rebase immediately before the push clears "CI rulebook freshness" and "submodule pointer backward" failures, so it is required whenever the branch conflicts. Resolve any conflicts, then re-run the relevant tests on the rebased result. The installed **pre-push hook** (`python3 knowledge/scripts/pr_missing_required_contexts.py`) only *warns* (it always `exit 0`s — never blocks) when the branch still conflicts with `origin/main`, so it is **not** the safety net — step 5.7's mergeability check is.
2.5. **🛑 Keep the local pre-push check deliberately small — compile the changed packages at most; do not grow a heavy pre-commit gate.** Pre-run the lane's fast mechanical guards **before the first push, not after CI rejects them**: `make preflight` (the repository's fast, deterministic mechanical checks, the *same* checks CI runs — see Step 1.6, so a locally-detectable red costs seconds here instead of a full 46–60 minute lane plus a log read) and `make validate-knowledge` for the corpus gate in particular (the same validators the pre-push hook enforces, plus `gen_requirement_status --check`). If either fails, the `git push` two lines down WILL be rejected by the hook for the same reason, or the PR will red on a mechanically detectable class. Fix what it names — a new probe needs its `+journey:` claim in the owning feature map, new deliverables need their commitment rows — and re-run until green, then push once. **Do not add compile-the-world or run-the-full-suite steps here:** the heavy lanes (unit / DB / e2e / coverage) are CI's job, and the per-wave pre-commit gate stays exactly the small, wave-local thing it is. The 33 policylint and 18 compile failures this command's own research found are **intentionally** not answered with a bigger local gate — they are answered by CI, and by fixing the branch when CI names them.
3. **🛑 Never push while CI is running on that PR unless the push fixes a failure — then disarm and push.** A push to a branch whose checks are in flight cancels them (GitHub supersedes the run on the new head), wasting the runner-minutes already spent on the superseded run (~19 min each) and, when the new commit is unrelated, buying nothing. So **batch your remaining commits — the flow-retro, notes, and any salvage — into the single final push**, and push again only when you have a failure to fix or a conflict to clear. If checks are pending and you have no failure to fix, **wait**; do not push. When you do push to fix a failure, first check for an existing PR for this branch — `gh pr list --head <branch> --json number,url,state` — and, since this mode arms auto-merge at open (step 5.8), run `python3 knowledge/scripts/gh_automerge_disarm.py <pr>` (idempotent; a no-op when nothing is armed) **before** `git push -u origin HEAD` — it also **dequeues** a PR that sits in a merge queue, whose branch is locked: GitHub rejects every push to a queued PR (`GH006` / HTTP 409 "Branches that are queued for merging cannot be updated"), and `gh pr merge --disable-auto` does **not** dequeue it — pushing onto a live auto-merge is the exact async-completion escape  recorded (PR #4185 merged with its force-pushed head's required `CI Success` check unregistered). A fresh PR (none exists) needs no disarm — step 5.8 arms it after creation, and step 4 reuses the check result.
4. From the check made in step 3: if a PR already exists for this branch, capture its number as `<pr>` and reuse it in steps 5–6 — never open a second PR for the same branch. If none exists, create one in step 5.
5. If no PR exists, create one. **Always reference the tracker issue key (`<KEY>`) in the title and body** when one resolved in Step 2 — that's what links the issue (and, for a completing title form / later `ship` keyword, what the daemon attributes as the closer — ):
   - Title: prefix with the key when known — `[<KEY>] <commit-subject summary>`.
   - Body: open with `PRD: knowledge/prds/NNNN-<slug>/prd.md` (when a PRD) and, **on its own line, a bare link — `Refs <KEY>` — NOT a closing keyword** (when a key resolved). A `Closes`/`Fixes`/`Resolves <KEY>` line here would auto-close the issue on merge even if this PR only *prepares* the work — the exact defect  exists to stop — so `push` mode never composes one; the closing keyword belongs on the **completing** merge only, which is `ship` mode's job (see the convention in Step 0). Use `gh pr create --title "..." --body "..."`.
   - **🛑 Always emit a `## Files` scope manifest ().** Compute the changed-file list with `git diff --name-only origin/<base>...HEAD` (three-dot; the merge-base of the base branch and HEAD) — and put every path under a markdown heading whose text is one of `Files` / `Changed files` / `Files changed` / `Files touched` / `Files modified` / `Changed paths` / `File manifest` / `Scope manifest`, as a bullet list of backticked paths (a trailing-slash directory entry covers its subtree). Example:
     ```markdown
     ## Files
     - ``
     - ``
     ```
     A Linear-keyed PR without a parseable manifest fails the consuming repo's scope-manifest CI guard; a declared path the diff does not carry, or a changed path the manifest does not name, fails too. Recompute and rewrite the section after every amend/rebase that changes the file set — a stale manifest is a red. When reusing an already-open PR, re-check the body carries a current `## Files` and `gh pr edit` it if not.
   - **Secondary issues fixed incidentally are referenced too — as links, never closing keywords, in `push` mode.** Scan the Autonomous Decisions Log content going into the body for any `Fixed incidentally: <KEY2>` marker (`autonomous-drive.md` Rule G — a secondary tracker issue whose root cause this diff actually resolves, e.g. a pre-commit gate forcing a fix in a file the primary change already touches). For each one, add its own `Refs <KEY2>` link (like the primary key, `push` mode composes **no** closing keyword — the `Fixes <KEY2>` line that closes it is composed by `ship`, the completing merge). A finding logged only as `Filed as follow-up: <KEY3>` (out-of-scope, not resolved here) stays a **plain link only** — no closing keyword for it ().
   - No work item and no key: still emit `## Files` (the guard only *requires* it when a Linear key is present, but emitting it always keeps the body honest); then `gh pr create --fill` is fine only when there is genuinely no composed body — otherwise compose the body with the manifest.
   - **🛑 A bare `<KEY>` mention elsewhere in the title/body does NOT satisfy this — see Step 5.5.**
5.5. **Verify the reference line actually landed — and that no closing keyword did (self-heal, don't just trust the composed prompt).** When a key resolved: `gh pr view <pr> --json body --jq .body | grep -Eiq '\b(refs|relates to|references|see)[[:space:]]+<KEY>\b'`. If it does **not** match — including when reusing an already-open PR whose body predates this rule — append the missing line via `gh pr edit <pr> --body "$(gh pr view <pr> --json body --jq .body)

Refs <KEY>"`. **Then confirm the PR does NOT carry a closing-keyword line for `<KEY>`**: `gh pr view <pr> --json body --jq .body | grep -Eiq '\b(close[sd]?|fix(e[sd])?|resolve[sd]?)[[:space:]]+<KEY>\b'` must be **FALSE** in `push` mode — a prep/partial PR that would close its issue on merge is the exact defect  exists to stop, so if a closing-keyword line is present, strip it back to a bare `Refs <KEY>` link (`gh pr edit <pr> --body "..."`). The closing keyword is authored only by the `ship` merge (the completing merge). **Repeat the same link+no-close check for every secondary key referenced in Step 5** — each needs its own `Refs` link and none may carry a closing keyword in `push` mode. Never report the PR as done without this check passing; a bare key mention does not even link the issue (see `tracking-and-execution.md` → "Branch-naming convention" and ).
5.7. **🛑 Verify the PR actually ended up mergeable — this is the ONE place the push rebases, and only when it must. Never leave a conflicting PR open.** Check `gh pr view <pr> --json mergeable,mergeStateStatus` once the PR exists. **If — and only if — `mergeStateStatus` is `DIRTY` or `mergeable` is `CONFLICTING`** (a branch that is merely `BEHIND` under required-status-checks-only protection is *not* a conflict and must NOT be rebased): `git fetch origin && git rebase origin/main`, resolve conflicts, re-run the relevant tests, and `git push --force-with-lease` — then re-check. Repeat bounded (≤3 rounds). This is the conflict-only rebase from step 2, applied at the point the push happens; a fresh PR that merges cleanly is never rebased, because rebasing it would only cancel its just-started CI. This is the human-facing mirror of `ship` mode's step-6 mergeability precondition; do not print the PR as done (step 6) while it is still conflicting.
5.8. **🛑 Arm auto-merge — the moment the PR opens, not after CI passes (; the golden rule "YOU OPENED IT, YOU OWN IT UNTIL IT MERGES").** A mergeable-but-unarmed PR is indistinguishable from a healthy one — no red check, no conflict, no queue entry — and sits open until a human sweep happens to look; the open→CI-green window is exactly the gap an after-CI arm leaves. **Skip only when the PR is a draft** (`gh pr view <pr> --json isDraft` → `true`): a third-party draft is a deliberate human pause and must not be armed — GitHub refuses auto-merge on a draft, and un-drafting it to arm would defeat the pause; its owner re-arms (§ [`verify.md`](verify.md) step 2). Otherwise arm, then confirm it actually armed (never assume — `tracking-and-execution.md` → "A third way auto-merge silently does not fire"):

   ```bash
   python3 knowledge/scripts/gh_automerge_arm.py <pr>     # arms, then confirms by reading it back
   python3 knowledge/scripts/gh_pr_merge_state.py <pr>   # must read armed / queued / merged
   ```

   The arm is confirmed by `autoMergeRequest` reading non-null **or** by a merge-queue entry: on a branch with a merge queue a PR whose checks are already green is **enqueued** instead of armed, and an enqueued PR reads `autoMergeRequest: null` — so `gh pr view <pr> --json autoMergeRequest` alone reports a queued PR as unarmed. `gh_pr_merge_state.py` reads both (plus `MERGED`); a plain `gh pr merge <pr> --auto --squash` is the arm either way, and never with `--delete-branch`, which `gh` refuses outright under a queue.

   **Expect `BLOCKED` — arming does not bypass any gate.** A `Type:bug`/`task`/`cleanup` PR is blocked by the required fix-gate check (`slot:git-workflow` names it) until `/fleet:verify` passes ( — the old "arming merges before the verifier finishes" reason is dead); a PRD is blocked by the required the plan gate check until the verify stamp; non-lane work (chores, docs) merges on green CI, which is that lane's whole gate. On a gated PR the arm set here **stands through the verify window** — the required check holds the armed PR `BLOCKED` until the verdict, so there is nothing to drop during verify (the  handoff draft hold that used to drop it is retired — ). It does **not** stand through the ship: ship mode disarms before its stamp push and re-arms only after the required checks report green on the stamped head ( — a head move or check re-dispatch under a live arm is the  class PR #10055 proved real; GitHub's async worker does not reliably re-validate a changed check state).
   **On a reused PR that is already mergeable, `--auto` merges immediately** — that is the arm working as designed (GitHub merges what its required checks have already cleared), not a mode confusion; still print the URL in step 6 and report the merge. If that reused PR touches `.github/workflows/**`, the immediate merge is refused under a scope-less token (`slot:git-workflow` — the third way auto-merge silently does not fire) — arm under the scoped token instead, read into the environment from wherever that slot says it lives, never inline into argv (; one instance of the general credentials-never-on-argv rule (CLAUDE.md)), then `python3 knowledge/scripts/gh_automerge_arm.py <pr>`.
5.9. **🛑 A fleet-dispatched coding run does NOT wait for CI — it ends `checks-pending`.** When this `push` is the open-PR step of an execute run whose dispatch mission teaches the done-sentinel status `checks-pending` ([`autonomous-drive.md`](../../process/autonomous-drive.md) → *The terminal: `checks-pending`*), the push is finished at the moment the checks are **dispatched** on the head you pushed, not when they are green: assert the PR head equals the remote ref (`gh api repos/{owner}/{repo}/pulls/<pr> --jq .head.sha` vs `git ls-remote origin <branch>`), assert `mergeStateStatus` is not `DIRTY`, assert `gh api repos/{owner}/{repo}/commits/<head-sha>/check-runs --jq .total_count` is non-zero, and **return that head SHA to the caller** for its done-sentinel (`verifiedSha`) — never `gh pr checks --watch`, never a sleep loop. The service watches the required checks on that head and moves the issue itself. **A person running `/fleet:push` interactively, or any run whose mission does not teach `checks-pending`, may still watch the checks here**, exactly as before.

### Mode: `merge`

1. Determine the base branch: `git merge-base HEAD main >/dev/null && BASE=main` (fall back to `master` if needed). Confirm with the user before proceeding if the base isn't obvious.
2. **Atomic-ship stamp (PRD only — BEFORE the merge).** If a PRD was detected (Step 2), while still on `<branch>`: open `knowledge/prds/NNNN-<slug>/prd.md`, set `status: shipped`, append `{ state: shipped, at: <>, by: push }` to `status_history`, and commit via the Commit contract as the **final branch commit** (`chore(NNNN, <KEY>): status: shipped`). This commit rides the merge so the status flip is **atomic** (Rule F). Non-PRD work: skip — the fleet daemon closes the tracker issue on a completing merged PR (; the tracker's keyword auto-close is dead).
3. `git fetch origin && git checkout <BASE> && git pull --ff-only`
4. `git merge --no-ff <branch>` (the status stamp from step 2 comes in with it). If the merge fails, stop — don't auto-resolve.
5. Run tests on the merged result (`make test-unit`). If they fail, **revert the merge** (`git reset --hard ORIG_HEAD`) and report. Don't push a broken merge.
6. `git push origin <BASE>`
7. `git branch -d <branch>` (use `-d`, never `-D` here — `-d` refuses if the branch is unmerged, which is the safety we want). **Then clean up the remote if the branch was ever pushed:** `git ls-remote --exit-code --heads origin <branch>` and, on a match (exit 0), `git push origin --delete <branch>`. (`merge` mode bypasses the PR, so GitHub's `delete_branch_on_merge` never fires for it — this is the only thing that removes the remote branch.)
8. Print the merge commit SHA. The PRD `status: shipped` is **inside** that merge commit — there is **no** separate status-flip commit (Rule F). **Tracker: no live mirror — the fleet projects it.** `shipped` is a projected transition (see `` → its tracker-sync section): once the merge to `main` (carrying `status: shipped`) lands, the `prd-projection` pass of the fleet's `corpus-sync` loop (`fleet-service`) moves the PRD issue to **Done** within the sync's interval — not on merge, and not when CI runs — and the fleet daemon's `_drive_to_done` settles non-PRD issues whose merged PR `_pr_completes_issue` ( — the tracker's keyword auto-close is dead).

### Mode: `keep`

1. Stop. Do nothing destructive.
2. Print: `Keeping branch <branch>. Push later with /fleet:push, or finish locally with /fleet:push merge.`

### Mode: `discard`

**Destructive.** Require an explicit typed confirmation before deleting any work.

1. Show the user exactly what will be lost:
   ```
   This will permanently delete:
     - Branch: <branch>
     - Commits ahead of <BASE>: <list of commit subjects with SHAs>
     - Any uncommitted changes (you confirmed the tree is clean — if not, stop now).

   Type the word `discard` to confirm.
   ```
2. Use `AskUserQuestion` with options `discard` / `cancel`. Only proceed on exact `discard`. Anything else → cancel.
3. Switch off the branch: `git checkout <BASE>`.
4. Force-delete the branch: `git branch -D <branch>`.
5. Print: `Discarded branch <branch>. <BASE> is now checked out.`

Note: `discard` does not flip any PRD status. The associated PRD stays at its previous status (likely `implementing`); the user can manually flip to `cancelled` (with `cancelled_reason:`) or move forward later.

### Mode: `ship` (open PR + auto-merge on green CI — autonomous flows)

The single rigorous land-on-`main` path that the **verifying** commands (`/fleet:prd:verify`, [`/fleet:verify`](verify.md)) delegate to once they have certified the work (it replaces the former direct-to-`main` mode). The execute commands that *wrote* the code — `/fleet:prd:implement`, `/fleet:task:implement`, `/fleet:bug:fix` — hand off at a green PR instead and never reach this mode. Hand it the **verified SHA** (the commit confirmed by the commit sub-task) and the **tracker issue key** (`<KEY>`, when resolved). It stamps the PRD status, pushes a branch, opens a PR, waits for CI, then squash-merges — so the merge **atomically** ships the status (Rule F) — and returns **one line** — the confirmed merge SHA on `origin/main`, or `NOT MERGED — <reason>` — the *only* evidence the caller treats as "shipped" ([`implementation.md`](../../process/implementation.md) §4b):

1. `git fetch origin`. Assert the working tree is clean and `git rev-parse HEAD` == `SHA`. Mismatch → `NOT MERGED — HEAD/SHA mismatch`.
2. **Reuse the issue's existing PR branch, else create a deterministic one.** When a tracker issue key is known, first look for an already-open PR for it: `gh pr list --search "<KEY>" --state open --json number,headRefName`. If one exists, `git fetch origin && git checkout <headRefName>` and move your commits onto it (rebase/cherry-pick) — push onto the **same** branch/PR; never open a second PR for one issue. Otherwise, if on `main`/`master`, create a **deterministic** branch from HEAD: `agent/<type>-<key>` (e.g. `agent/fix-eng-160`, `agent/prd-0015-eng-152`) — **no per-user prefix and no slug**, so any box or retry resolves the *same* name and finds the *same* PR. Carry the tracker issue key. Never push autonomous work directly onto `main`.
2b. **🛑 Rebase only when the PR is `CONFLICTING` — never merely to be current (mirrors default `push` mode step 2).** `main` requires status checks, **not** an up-to-date branch, so a branch that is merely *behind* `main` still gets a merge ref and its `pull_request` CI still runs. Do **not** run `git rebase origin/main` here on principle: a rebase rewrites every commit SHA and cancels the PR's in-flight CI for nothing (base-sync rebases were 46% of the superseding pushes the  research measured). The conflict check is step 6's mergeability precondition, run **before** arming and **immediately before the push that needs it**: `gh pr view <pr> --json mergeable,mergeStateStatus`; only on `DIRTY` / `CONFLICTING` do `python3 knowledge/scripts/regen_reconcile.py --base origin/main` — **the non-authoring reconcile, never a rebase** (). Ship mode's **only** caller is a verifying session, which may not author: a rebase rewrites every certified commit, while `regen_reconcile.py` merges `origin/main` and proves the branch's own diff byte-identical. On its exit 0, `git push origin HEAD` (a fast-forward — **never** `--force`) and continue at the new head; on exit 1/2 the conflict is real work — report `NOT MERGED — conflict with the base` and let the caller route the conflict-as-work hand-back. The one thing 2b still guarantees is that a push happens with the branch in a pushable state: if it already conflicts, the conflict is reconciled here or at step 6's precondition, never pushed through and left `DIRTY`. **A `DIRTY` PR is GitHub telling you it cannot compute a merge ref, so `pull_request` CI never starts** — but `DIRTY` means *conflicting*, not *behind*; conflating the two is why the old unconditional rebase existed.
3. **🛑 Atomic-ship stamp (PRD only — the load-bearing step).** If a PRD was detected and verify is shippable (all-PASS or pass-with-follow-up per `prd:verify` Step 4 Path A): on the work branch, set `status: shipped`, append `{ state: shipped, at: <>, by: ship }` to `status_history`, and commit via the Commit contract as the **final branch commit** (`chore(NNNN, <KEY>): status: shipped`). This commit becomes part of the PR head, so the squash-merge in step 6 lands `status: shipped` on `main` in the **same commit** — the merge IS the ship (Rule F). Non-PRD work (bug/task): skip — the fleet daemon closes the tracker issue when a merged PR `_pr_completes_issue` (completing title form *or* a closing keyword; ). A bare body mention alone is not enough; compose the keyword at arm time (step 5 / 5.5 / ) so attribution cannot race the merge. (Why stamp *before* CI: only `main` is authoritative and the merge fires only on green, so the branch transiently carrying `shipped` is harmless — while it guarantees CI validates the exact content that ships.) **If a PRD was detected and this stamp does NOT land** (verify was not shippable, or any other reason this merge will not carry `status: shipped`) — do not skip silently past it: step 5.6 below checks for exactly this and strips the closing keyword before the merge in step 6, so a partial/withheld ship never claims the tracker issue it doesn't complete.
3b. **Pre-run the lane's fast mechanical guards (`make preflight`) and the knowledge gate (`make validate-knowledge`) before the push** — same rationale as `push` mode's step 2.5: the pre-push hook enforces these validators, and a rejection here costs a full push→fix→force-push round trip through step 6's re-merge-able loop.
3c. **🛑 Resolve the PR this mode reuses, and disarm it before any push ( /  class).** When a tracker issue key is known, search for the already-open PR now — `gh pr list --search "<KEY>" --state open --json number,headRefName,url` (fall back to `--head <branch>`) — and capture `<pr>`; step 5 reuses this result. **If a PR exists, run `python3 knowledge/scripts/gh_automerge_disarm.py <pr>` before step 4's push** (idempotent — a no-op when nothing is armed; also drops any arm a caller left live, e.g. verify.md §6 step 4's re-arm): push mode's open-time arm (step 5.8, ) stands through the whole verify window, and pushing the atomic-ship stamp under it is the exact escape  recorded — the head moves, the plan gate re-dispatches on the new SHA, and GitHub's async auto-merge worker can complete the merge without re-validating the new head's required checks (PR #10055 merged 18s before its re-run went green; PR #4185 merged with the new head's checks unregistered). If none exists, nothing is armed yet — the only arm this mode sets is step 6's, after the required checks are green.
4. `git push -u origin HEAD` (the PR head now contains the status stamp).
5. **Open (or reuse) the PR**, carrying the tracker issue key. Search by the **tracker issue key** (not just the branch head) so a PR opened under a different branch name (another box, an earlier attempt) is still found and reused: `gh pr list --search "<KEY>" --state open` (fall back to `--head <branch>`). If an open PR exists, push to it — **do not create a second**. If none, `gh pr create --title "[<KEY>] <feature>" --body "<PRD link + Closes <KEY> + decisions-log/verify summary + ## Files manifest>"`. **🛑 The body MUST carry a literal `Closes <KEY>` / `Fixes <KEY>` / `Resolves <KEY>` line** — the daemon's strongest attribution signal for `_pr_completes_issue` (: the tracker's keyword auto-close is dead; the fleet daemon is the closer). A bare body mention alone does not complete; a completing title form (`fix(<KEY>): …` / `[<KEY>] …`) is the other arm (). Compose the keyword at arm time () so the merge cannot race the body edit. **🛑 The body MUST also carry a current `## Files` scope manifest** (same rule as `push` mode step 5 — ): `git diff --name-only origin/<base>...HEAD`, every path as a backticked bullet under `## Files`. Recompute after the atomic-ship stamp if that commit added paths; on a reused PR, rewrite a stale section with `gh pr edit`. **Any `Fixed incidentally: <KEY2>` marker in the Autonomous Decisions Log** (`autonomous-drive.md` Rule G — a secondary tracker issue whose root cause this diff actually resolves) **gets its own `Fixes <KEY2>` line composed into the body too** — not just a bare mention or link; a marker logged as `Filed as follow-up: <KEY3>` (deferred, not fixed) stays a plain link ().
5.5. **Verify the closing-keyword line actually landed — self-heal, don't trust the composed prompt.** When a key resolved: `gh pr view <pr> --json body --jq .body | grep -Eiq '\b(close[sd]?|fix(e[sd])?|resolve[sd]?)[[:space:]]+<KEY>\b'`. Closes <KEY>"`. This is the completing merge, so appending `Closes <KEY>` here is correct — it is precisely the close that `push` mode deliberately withheld when it opened the PR. **Repeat this check for every secondary key composed in step 5 (`Fixed incidentally` markers)** — each needs its own verified closing-keyword line, or that secondary issue silently sits `In Progress` after merge (). Do not proceed to step 6 until all of these checks pass.
5.6. **🛑 For a PRD-linked key, verify the closing keyword is NOT present unless THIS merge actually carries `status: shipped` — the converse of 5.5, and just as load-bearing ().** A closing keyword is a completing claim the fleet daemon's `_pr_completes_issue` accepts (and, before  disabled keyword auto-close —  confirmed it no longer fires — GitHub's tracker integration closed the issue the moment the PR merged, regardless of frontmatter). That made it a second, uncontrolled writer to a PRD-linked tracker issue's state alongside the `prd-projection` pass of the fleet's `corpus-sync` loop's git→tracker projection (`tracking-and-execution.md` → its tracker-sync section). The guard still holds under the daemon closer: a keyword on a non-`shipped` PRD PR would let the daemon settle the issue while git still says `implementing`. Before step 6, when a PRD was detected: ask `python3 knowledge/scripts/validate_prd_verify_ship.py <NNNN> <KEY> --pr <pr>` whether this merge may carry the ship — it reads the plan's own recorded state at the branch HEAD you are about to push, not only the verdict. If it refuses (step 3's stamp did not land — verify wasn't shippable, an interrupted run, or any other reason), the merge you are about to make must not claim an issue for a deliverable that isn't done: strip any `Closes <KEY>` / `Fixes <KEY>` / `Resolves <KEY>` line for the **primary** key from the PR body (`gh pr edit <pr> --body "..."`, keeping a bare `<KEY>` mention so the link survives — only the closing verb goes). This is exactly the failure  named: PRD 0359's in-repo PR merged (green, real, valuable — its cross-repo `-infra` companion was still outstanding) with `status: shipped` correctly withheld, but the `Closes ` line composed back when `/fleet:prd:implement` opened the PR rode the merge anyway and closed the tracker issue regardless. Non-PRD work (bug/task) is unaffected — there is no frontmatter `status:` to check; the daemon closes those issues when the merged PR `_pr_completes_issue` (title-shape or keyword).

By verdict:
     - **`merged`** (exit 0) → proceed to step 7.
     - **`ejected`** (exit 4) — **REMOVED FROM THE MERGE QUEUE.** The PR now reads `OPEN` / `CLEAN` / nothing armed / nothing queued with every required check on its own head still green — the one reading every other signal calls healthy. The script names the removal reason and the red check-runs on the `merge_group` commit (usually a semantic clash with a PR merged ahead of it). Treat it exactly as red CI: report `NOT MERGED — removed from the merge queue: <reason>, <checks>` and, on a fix, `git fetch origin && git rebase origin/main`, fix at the root cause, push, and **re-enter step 6 from the top** (which re-arms). Never re-arm an unchanged head — the queue rebuilds the same group and ejects it again.
     - **`conflicting`** (exit 3) → the mergeability precondition above: rebase, push, re-enter step 6.
     - **`unarmed`** (exit 5) — open, nothing armed, nothing queued, no ejection: nothing will ever merge it. Re-enter step 6 from the top.
     - **A required check that was green goes red before the merge lands** (a late re-dispatch, a flake) → `python3 knowledge/scripts/gh_automerge_disarm.py <pr>`, then report `NOT MERGED — CI failed: <check>` and re-enter step 6 from the top on a fix — never a bare re-push onto the armed `--auto`.
     - Anything else pending far past every-green → re-check the mergeability precondition and Precondition 2 before assuming a GitHub-side fault.
7. **Confirm the merge landed.** `git fetch origin --prune`; assert `gh pr view <pr> --json state` is `MERGED` and `git rev-parse origin/main` advanced to include the squash commit. Mismatch → `NOT MERGED — merge not reflected on origin/main`. Then `git checkout main && git pull --ff-only` to sync local — **do NOT write any status here; `main` already carries `status: shipped` from the merge** (a post-merge status commit is banned, Rule F). **Tracker: no live mirror — the fleet projects it.** For a PRD-linked key the merge to `main` (carrying `status: shipped`, and with step 5.6's confirmation the keyword was only present when that stamp landed) is projected by the `prd-projection` pass of the fleet's `corpus-sync` loop → **Done**, within the sync's interval rather than on the merge. For bug/task/cleanup the fleet daemon's `_drive_to_done` settles the issue once a merged work-branch PR `_pr_completes_issue` (completing title form or the closing-keyword line step 5.5 verified before merge) — the tracker's keyword auto-close is **dead** ( / ).
7b. **Verify the head branch is gone — self-heal if it lingers (don't trust `delete_branch_on_merge` blindly).** After the merge, confirm the remote branch was actually deleted: `git ls-remote --exit-code --heads origin <branch>`. A **non-zero** exit (ref not found) is the pass — the branch is gone (via the repo's `delete_branch_on_merge`; the arm carries no `--delete-branch`, which `gh` refuses under a merge queue). If it **still exists** (exit 0 — e.g. a concurrent process re-pushed it, or the setting is off on this repo), delete it: `git push origin --delete <branch>`. Never leave a merged PR's head branch on origin — leaked merged branches are exactly the debt the  sweep cleared (1,253 branches, ~95% of them merged-PR leftovers). Also drop the stale local ref: `git branch -D <branch>` (safe — the work is on `main`).
8. Print the confirmed `origin/main` merge SHA (or `NOT MERGED — <reason>`).

No standalone test run (the caller already verified); CI is the gate. Interactive review uses `push` (open PR, stop).

## Commit contract

The canonical commit discipline (formerly ``). `push` (default <!-- -refs:skip -->
mode) runs it on any pending changes; `/fleet:prd:implement`
dispatches commit sub-agents that follow it. **Do not consider a commit done until
pre-commit passes AND `HEAD` has moved.**

**Policy — fix everything, never loosen.** Fix **all** failures — including
pre-existing ones unrelated to the current change. You are **not** allowed to skip
a failure because "it was already broken" or "not my change", and **not** allowed
to loosen lints or lower coverage thresholds. If coverage is below the gate, write
tests to raise it — now, not deferred. Never `--no-verify`.

1. **Stage by explicit path** (`git add <path…>`, or `git add -u` to re-stage
   tracked edits) — never blind `git add -A`, which sweeps unrelated in-flight
   working-tree changes.
2. **Commit:** `git commit` with a message that summarizes the change. If the user
   supplied a message, use it; otherwise infer a concise subject from the staged
   diff (no generic "chore: fix pre-commit"). **Reference the work item's the tracker
   issue key** (`<KEY>`) in the subject scope when the branch carries one —
   `feat(NNNN, <KEY>): …` / `fix(<KEY>): …`. No "Test plan" section in commit
   bodies (those belong in PRs). **Run the commit in the FOREGROUND — never
   background-bash — whenever the session may be resumed/torn down mid-turn (always
   under the headless `linear-agent` daemon), and
   `pkill -9 -f 'pre-commit-parallel'` to reap orphaned gate procs before each
   attempt — BEFORE the attempt only, and only orphans: a hook proc from THIS
   attempt is never killed (killing a live hook is what strands `.git/index.lock`
   and costs a recovery loop), so if the same turn has already started a commit,
   wait inside the session's declared blocked-wait instead (the daemon supervisor
   honors it). See [`implementation.md`](../../process/implementation.md) §4.** A backgrounded ~1–2-min
   pre-commit is reaped by turn-teardown
   before HEAD moves — spiraling resume-nudges and OOM-contending orphans (see
   [`implementation.md`](../../process/implementation.md) §4).
3. **Fix and retry:** if the pre-commit hook rejects the commit, fix each failure,
   re-stage, and retry until it succeeds with zero hook failures:
   - **index desync after a revert:** if a hook (e.g. lint-staged) *reverts* its
     partial changes on failure, the index is left out of sync with the worktree —
     re-stage tracked files with `git add -u` (or `git add <absolute-path>`) before
     the next attempt; never retry on a half-staged tree.
   - **a formatter hook** (whitespace, end-of-file, the language formatter) fixed files
     in place → `git add -u`, retry.
   - **a lint hook:** run `make lint-fix` FIRST (auto-applies mechanical fixes +
     reconciles imports), then fix any remaining violations by hand at the boundary —
     never add baseline entries beyond the sanctioned cases `make lint` names —
     `git add -u`, retry.
   - **the unit / coverage lane:** fix ALL failing tests (even pre-existing); write tests
     to raise coverage above the gate → `git add -u`, retry.
   - **the contract lint** (where `slot:api-contract` names one): fix the spec so it
     passes → stage the spec, retry.
   - **generated-code:** `make generate`, then `git add` the generated paths,
     retry.
   The hooks themselves, and what each one runs, are `slot:gate`'s answer.
   - **ruff:** `uv run ruff format && uv run ruff check --fix` → `git add`, retry.
   - **validate-tracking-metadata:** fix the dangling/off-enum frontmatter (a
     `cancelled` PRD needs `cancelled_reason:`) → re-stage, retry.
4. **Verify it landed (load-bearing).** A streamed "committed" line is NOT proof.
   Capture `BEFORE=$(git rev-parse HEAD)` and `AFTER=$(git rev-parse HEAD)` around
   the commit and assert `AFTER != BEFORE`. An unchanged HEAD means the commit was
   **rejected** — go back to step 3.
5. **Report the verified SHA** (`git log --oneline -1`). That SHA is the result a
   caller relies on — never claim "committed" without it.

If the diff delivers a capability tracked in `knowledge/features/` (touched paths →
`python3 knowledge/scripts/component_of.py <path>` → the component's areas), verify the row's
`Ships in` no longer reads `—`: PRD work cites the PRD number (prd:create's flip step),
